\section{The fine-tuning pilot}
\label{app:lora}

The pilot tested LoRA updates to the pinned Qwen3.5 27B on one H100. An Apptainer runtime used an isolated network namespace, read-only inputs, no credentials, and a per-attempt writable image. An external positive control verified that the network test could succeed outside isolation; it failed inside. Base weights were hashed before each process and after each stage.

LoRA adapters updated query and value projections in the full-attention layers, using fp32 adapters on a frozen bf16 base. Smoke, training, and fresh-process reload stages tested attachment, saving, reloading, disabling, and stress cycles (Figure~\ref{fig:lora}a). All integrity and containment checks passed. Reproduction comparisons had zero logit difference where equality was expected, while the trained adapter differed from the base. Diagnostic performance improved from \N{lora.diag.before} to \N{lora.diag.after} of 16 questions, with no newly wrong answer. The stages used \N{lora.minutes.used} of \N{lora.minutes.reserved} reserved GPU-minutes.

A later profile placed the reserved-memory limit near \N{lora.gate.tokens} tokens at the 85\% limit (Figure~\ref{fig:lora}b), which excludes \N{lora.over.gate.pct} of study-like examples, whose median length is \N{lora.median.tokens}. These checks establish an engineering capability, not the effectiveness or detectability of a biased adapter.
